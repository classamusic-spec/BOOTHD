# CLAUDE.md — Porcelain Photo Booth / mandatory repository rules

## Non-negotiable product decisions
Build **one Flutter/Dart codebase supporting iPadOS and Android tablets as equal first-release targets**. This is the final platform decision. Do not switch to SwiftUI-only, React Native, a web wrapper, or defer Android to a later port. Native Swift/Kotlin code is acceptable ONLY for evidenced platform gaps behind narrowly scoped platform interfaces. Built-in cameras, offline-first, Porcelain neumorphic UI, two guest orientations, full layered editor in v1, full-resolution export, export-only printing until hardware chosen, commercial-device certification: ALL locked. Owner-approved exception (ADR-0018): the same codebase also builds for the web as a test and demonstration target only; it is not a release platform, not certified and not a kiosk, and web differences stay in infrastructure adapters.

## Before coding
Read `START_HERE.md`, `prompts/MASTER_PROMPT.md`, `docs/FLUTTER_PLATFORM_STRATEGY.md`, `docs/PRODUCT_SPEC.md`, `docs/ARCHITECTURE.md`, `docs/UX_SCREEN_SPECS.md`, current milestone prompt, and its AC requirements. Inspect existing code, Git status, Flutter/Dart/Xcode/Android SDK, attached devices, and test output. Make a short change plan; identify both-platform consequences and dependency/library risks. Do not silently widen scope.

## Execution discipline
Implement **only** the owner's explicitly assigned milestone. One milestone, one acceptance report, then STOP. Follow order **M00→M01→M02→M03→M04→M05→M06→M07→M08→M09→M10→M11→M12**. M01 is a technical proof milestone BEFORE the full visual design system. Never mark physical camera tests PASS unless actual physical hardware ran. If device unavailable: BLOCKED with commands/manual procedures, not fictitious success. Evidence entries must reference `AC-xxxx` and include tested devices, OS/build, commands, exit codes, and artifacts. Maintain `docs/IMPLEMENTATION_LOG.md`, `docs/ACCEPTANCE_EVIDENCE.md` and ADRs.

## Architecture
Flutter/Dart shared: UI, design tokens, app state, events, template document, geometry/scene graph, layers, editor gestures, render semantics, session state machine, storage/backup policy and export pipeline. Riverpod for state/DI; GoRouter for routes and guest isolation; Drift/SQLite structured storage; managed application files for photo/image bytes. Camera plugin (`camera`, Android endorsed CameraX, iOS AVFoundation-backed) behind a `CameraService`, not called directly from guest UI. A small plugin/native bridge is an escape hatch, not the default architecture. No network dependency for core capture/editor/events/export. APPROVED EXCEPTION: optional authenticated delivery backend for MMS preview + private full-quality download link; implement strictly in M09 with user consent, secure server-side messaging, retention and delivery state. No DSLR, unsolicited email/SMS/marketing, AI, GIF/video or printer drivers in release 1.

## Approved optional online phone delivery — M09
Phone delivery is now INCLUDED as an independently toggleable commercial feature: MMS JPEG preview + cryptographically unguessable expiring link to the full-quality **finished composition**. Internet usually available but guest capture/gallery/render/export ALWAYS work offline; no sends without explicit checkbox consent. Only backend can call Twilio; Flutter must not include messaging keys. All phone-delivery feature settings OFF before sender/credentials/legal preflight. US sender registration, STOP/HELP, strict quotas, durable short-lived queue, safe retries and webhook signature validation required. Twilio must fetch an HTTPS publicly reachable *preview-only* media URL; guest full-resolution files live in private storage with revocable grants. A provider's sent status is not delivered/read. Read `docs/PHONE_DELIVERY_SPEC.md`, `docs/PHONE_DELIVERY_UX.md` and `docs/PHONE_DELIVERY_ACCEPTANCE.md` before M09. No marketing messages.

## Early proof-of-feasibility M01
Prove on available platforms: sample 4×6 / 1200×1800 pixel layered rendering from original fixture images; 2 photo slots; transparent PNG crossing both photo boundaries and optionally extending outside a slot; golden geometry/alpha assertions; one permission-aware real still capture on iPad AND Android with saved file validation. For physically missing devices label that subgate BLOCKED. This stage is deliberately technically ugly, minimal UI; do not spend time on dashboard polish. Record CPU/GPU memory, render time, still capture dimensions, orientation and lens where possible. M04/M06 mature the spike into production modules.

## Template and rendering invariants
Use versioned JSON with stable IDs, immutable revisions, asset references, explicit page units/dpi, relative/normalized geometry, transforms, z-order, rotation pivot and crop/focal metadata. Clip captured photos to their own photo slots only; unrelated transparent PNG/image layers are NEVER implicitly clipped by slot masks. Editor may show off-page decoration; final export clips to page/bleed boundary. Preview and full-resolution export share scene-graph semantics. A 4×6 at 300 DPI must export at 1200×1800 pixels. Never use an editor screenshot as final print. Render from unmodified originals with bounded memory, validated output and atomic file commits. Test transparent-alpha fringes, text, crop, rotation, masking, missing assets and repeated renders on both platforms.

## Camera invariants
Prefer official maintained Flutter camera plugin; verify supported APIs and versions and pin lockfile. Camera lifecycle is app-managed (suspend/dispose/re-init on app state changes). Serialize capture and initialization. Distinguish sensor EXIF orientation, screen/window orientation, mirror preview, mirror saved photo and photo-slot crop. Do not capture if app no longer active. Verify still file exists, decodes and is persistently committed before claiming saved. Retakes create new immutable files. No preview screenshots as photos. Permission denial and plugin errors must surface actionable guest-safe/operator details.

## Adaptive orientation
A booth's portrait/landscape setting is a **preferred presentation**; the *effective* screen orientation/window bounds come from the OS. On iPad orientation requests may require Requires Full Screen / disabled multitasking; record the deployment tradeoff. On Android >=16 with >=600dp and suitable target API, orientation requests may be ignored; Android 17/API 37 removes the prior large-screen opt-out. Build adaptive PortraitGuestLayout and LandscapeGuestLayout selected based on actual constraints, and show operator warnings if preference cannot be enforced. Explicitly separate output template portrait/landscape from device UI orientation. Verify correct lens preview/mirroring on both platforms in both orientations.

## Offline data and security
Drift/SQLite transactions are not filesystem transactions: stage/write/validate/rename and journal pending operations with startup reconciliation. Do not mutate original photos. Save event/template/session revision mappings and support recovery of incomplete renders. Validate archive import against traversal/zip bombs, invalid assets and oversized files. Never depend on temporary file picker URIs. PIN protected operator routes; store only appropriately protected slow salted verifier, with rate limiting and recovery protocol. Never log photo data, secrets or guest PII. Support operator-controlled retention/deletion and verified backup/restore; no networking required.

## Porcelain UX
Default Porcelain Studio theme: warm ivory, champagne-gold accent, charcoal readable text, tactile raised/inset components, subtle animations, readable focus/contrast and reduced-motion behavior. Semantically tokenized style. Studio responds in both tablet orientations; booth supports configurable portrait and landscape with effective size fallback. Guest controls large and simple; no access to Gallery/Studio, photos from prior session, platform file dialogs, diagnostics, or system share sheet. Do not add dead buttons, pretend to print/save/test, or render raw exception screens to guests.

## Tests/builds
After appropriate increments run `dart format --output=none --set-exit-if-changed .`, `flutter analyze`, `flutter test`, renderer golden/unit tests, Drift migration/recovery tests, and accessible device/simulator builds. At M00 and M01 report exact feasibility of `flutter build ios` (macOS/Xcode only) and Android build. Both devices required for release candidate. Official integration_test plus native permission UI manual or specialized integration tests, as necessary. Cross-platform golden tolerance must be defined; don't pass by making tolerances useless. Never fabricate success or change assertions simply to pass tests.

## Reporting and stop rule
For EVERY milestone report: ID/revision; plan/outcomes; changed files; migrations; commands/exits; precise iPad tests; precise Android tests; fixture results; AC ID statuses PASS/FAIL/BLOCKED; security/privacy notes; risks; next milestone. Stop for owner approval. Only owner can declare GO on M12. Printer support is outside this release until hardware chosen. Phone delivery is an OPTIONAL network-dependent capability requiring separate credentials, registered sender, consumer consent and real end-to-end evidence before enabling.
